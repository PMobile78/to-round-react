# Этап 0: общий формат данных v2 и перевод веба — спецификация

Дата: 2026-10-14. Статус: на согласовании.
Связано: [дорожная карта](2026-10-14-android-roadmap.md).

## 1. Цель

Подготовить данные и сервер к двум клиентам — вебу и нативному Android-приложению:

- описать единый формат данных v2 (контракт), который одинаково читают и пишут оба клиента;
- перевести на него веб, Cloud Functions и правила Firestore;
- перенести существующие данные без потерь, с бэкапом и возможностью отката.

Этап выполнен, когда веб, функции и правила работают только с форматом v2, данные перенесены и проверены, а напоминания приходят.

## 2. Решения

- Веб можно менять как угодно: им пользуется только владелец. Обязательное условие — бэкап задач перед переездом.
- Все данные и настройки хранятся только в Firestore. Копии в localStorage убираются. На устройстве остаются только позиция кнопки «+», последняя открытая карта mindmap (код карт в этапе не меняется), id установки Firebase (его хранит SDK) и кэш Firestore.
- Задачи, категории и устройства — по документу на запись; настройки — одним объектом.
- Описания — Markdown (раздел 5).
- Повтор — единицы `hours`, `days`, `weeks`, `months`. Напоминания — только целые часы и больше.
- «Готово» у повторяющейся задачи переносит срок на ближайший будущий раз; «Завершить серию» — отдельное действие. Просроченная повторяющаяся задача остаётся просроченной до «Готово»; сервер сроки не двигает.
- На каждом устройстве — переключатель «получать напоминания здесь».
- Планировщик уведомлений — каждую минуту.
- Перенос данных выполняет веб при первом входе новой версии, с окном предпросмотра.
- Mindmap в этап не входит: коллекция `user-mindmaps` и код карт не меняются.

## 3. Структура Firestore

```
users/{uid}                          документ пользователя: settings и служебные поля
users/{uid}/tasks/{taskId}           задачи
users/{uid}/categories/{categoryId}  категории
users/{uid}/devices/{deviceId}       устройства; deviceId = id установки Firebase
user-mindmaps/{uid}/maps/{mapId}     без изменений
notification-sent/{key}              служебная, только сервер, без изменений
```

Старые коллекции после переезда доступны только для чтения, позже владелец удаляет их вручную: `user-bubbles/{uid}` вместе с `bubbles/*`, `user-tags/{uid}`, `user-fcm-tokens/{uid}/tokens/*`.

Идентификаторы: новые записи получают автоматический id Firestore. Перенесённые задачи и категории сохраняют свои прежние id.

Общие правила для всех документов ниже:
- поля, не помеченные как необязательные, присутствуют всегда;
- `Timestamp` создания и изменения ставит сервер (`serverTimestamp()`);
- клиенты пишут только частичные обновления изменённых полей и не меняют служебные поля сервера: при создании задачи клиент пишет `overdueAt: null` и не пишет `nextNotifyAt`, при изменениях не трогает оба поля;
- существующий документ клиент целиком не перезаписывает: при изменении правила требуют прежние `createdAt` и служебные поля, а `updatedAt` — время сервера (раздел 7), поэтому `setDoc` поверх существующего документа отклоняется. Создать документ с исходными датами можно только с id, которого ещё нет.

### 3.1 Задача — `users/{uid}/tasks/{taskId}`

| Поле | Тип | Ограничения и смысл |
|---|---|---|
| `schemaVersion` | int | `2` |
| `title` | string | 1–1000 символов после обрезки пробелов |
| `description` | string | Markdown (раздел 5), 0–100 000 символов |
| `categoryId` | string или null | id категории; ссылка на несуществующую категорию означает «без категории» |
| `status` | string | `active`, `done` или `deleted` |
| `due` | map или null | `{ local: "YYYY-MM-DDTHH:mm", tz: "<зона IANA>" }`, см. 4.2 |
| `reminders` | list&lt;int&gt; | минуты до срока; каждое значение кратно 60, от 60 до 524 160 (52 недели); без повторов, по возрастанию, не больше 10; пустой список, если `due == null` |
| `repeat` | map или null | `{ every: 1–999, unit: "hours" \| "days" \| "weeks" \| "months", weekdays?: list<int 1–7>, monthDay?: int 1–31 }`; `weekdays` допустимо только при `unit == "weeks"`; `monthDay` обязательно при `unit == "months"` и запрещено при других единицах; `null`, если `due == null` |
| `radius` | int | 30–80, размер пузыря; по умолчанию 45 |
| `pulseMuted` | bool | пользователь остановил пульсацию текущей просрочки |
| `overdueAt` | Timestamp или null | момент, когда сервер отметил просрочку; пишет только сервер |
| `nextNotifyAt` | Timestamp, необязательное | ближайшее событие уведомления; пишет только сервер |
| `createdAt` | Timestamp | время создания |
| `updatedAt` | Timestamp | время последней записи клиента |
| `deletedAt` | Timestamp или null | не `null` тогда и только тогда, когда `status == "deleted"` |

### 3.2 Категория — `users/{uid}/categories/{categoryId}`

| Поле | Тип | Ограничения и смысл |
|---|---|---|
| `schemaVersion` | int | `2` |
| `name` | string | 1–100 символов после обрезки; уникальность среди категорий пользователя проверяет клиент |
| `color` | string | один из 20 цветов палитры `contract/palette.json`; уникален среди категорий пользователя (проверяет клиент), поэтому категорий не больше 20 |
| `order` | number | порядок по возрастанию |
| `createdAt`, `updatedAt` | Timestamp | время создания и изменения |

Палитра переносится в `contract/palette.json` из `src/hooks/tagColors.js`, и веб начинает брать её оттуда.

### 3.3 Устройство — `users/{uid}/devices/{deviceId}`

| Поле | Тип | Ограничения и смысл |
|---|---|---|
| `platform` | string | `web` или `android` |
| `fcmToken` | string или null | токен FCM; `null`, если разрешения нет или FCM признал токен недействительным |
| `notificationsEnabled` | bool | переключатель «получать напоминания здесь» |
| `createdAt`, `updatedAt` | Timestamp | время создания и изменения |

`deviceId` — id установки Firebase: `getId()` в вебе, `FirebaseInstallations.getInstance().id` на Android. На Android `fcmToken` — адрес, который FCM сообщил приложению после регистрации по id установки: сам id установки (сервисы Google Play 26.12 и новее) или токен FCM на более старых; FCM принимает оба в поле `token` сообщения (уточнено в этапе 3, [спецификация](2026-10-24-stage-3-notifications-design.md)). Новое устройство регистрируется с включённым переключателем, разрешение на уведомления запрашивается после входа, как сейчас. При выходе из аккаунта клиент удаляет документ своего устройства до вызова `signOut`. Регистрация при входе: если документ устройства уже есть — `updateDoc` с новым `fcmToken` и `updatedAt` (переключатель не трогается); если нет — `setDoc` со всеми полями и `createdAt`/`updatedAt` = `serverTimestamp()`.

### 3.4 Документ пользователя — `users/{uid}`

| Поле | Тип | Ограничения и смысл |
|---|---|---|
| `schemaVersion` | int | `2` |
| `settings` | map | раздел 3.5 |
| `migration` | map, необязательное | `{ fromV1At: Timestamp, tasks: int, categories: int }`; пишется по завершении переноса |
| `createdAt`, `updatedAt` | Timestamp | время создания и изменения |

Документ создаёт клиент при первом входе — с настройками этого браузера (3.5). Если первый вход не смог его создать (без сети), клиент создаёт его, как только сервер подтвердит, что документа нет, а перенос (9.1) — в своём конце, если документа всё ещё нет. `migration` пишется в конце переноса.

### 3.5 Настройки — `users/{uid}.settings`

| Поле | Значения | По умолчанию | Откуда при переносе (localStorage) |
|---|---|---|---|
| `themeMode` | `light`, `dark`, `system` | `system` | `app-theme-mode` |
| `design` | `classic`, `modern`, `aurora`, `brutalist`, `clay` | `classic` | `app-design` |
| `language` | `en`, `uk` | язык экрана входа (сначала это язык устройства): `uk*` → `uk`, иначе `en` | `i18nextLng` |
| `mainView` | `bubbles`, `list` | `bubbles` | `bubbles-main-view` (`tasks` → `list`) |
| `labelFontSize` | int 8–20 | 8 | `bubbles-font-size` |
| `bubbleBackground` | bool | `true` | `bubbles-background-enabled` |
| `showCategoriesPanel` | bool | `false` | `bubbles-categories-panel-enabled` |
| `showInstructions` | bool | `true` | `bubbles-show-instructions` |
| `bubbleFilter` | `{ categoryIds: list<string> \| null, showUncategorized: bool, plannedOnly: bool }` | `{ null, true, false }` | `bubbles-filter-tags`, `bubbles-show-no-tag`, `bubbles-planned-tasks-only` |
| `listFilter` | `{ categoryIds: list<string> \| null, showUncategorized: bool }` | `{ null, true }` | `bubbles-list-filter-tags`, `bubbles-list-show-no-tag` |
| `listSort` | `{ by: "createdAt" \| "updatedAt" \| "title" \| "category", order: "asc" \| "desc" }` | `{ updatedAt, desc }` | `bubbles-list-sort-by` (`tag` → `category`), `bubbles-list-sort-order` |

`categoryIds: null` означает «все категории»; список — явный выбор.

Настройки записываются по отдельным полям (`settings.themeMode` и т. п.) вместе с `updatedAt`, чтобы два устройства не затирали чужие изменения. До входа в аккаунт экран входа использует язык устройства и системную тему; язык, выбранный на экране входа, становится языком нового аккаунта. После входа применяются настройки пользователя.

На устройстве остаются `bubbles-fab-position` и `mindmap-last-open-id`. Неиспользуемый ключ `bubbles-use-rich-text` удаляется.

## 4. Поведение

### 4.1 Жизненный цикл задачи

- **Создание:** `status = active`, `pulseMuted = false`, `overdueAt = null`, `deletedAt = null`.
- **«Готово» у задачи без повтора:** `status = done`. `due`, `reminders` и `repeat` сохраняются как история, уведомлений по задаче больше нет.
- **«Готово» у повторяющейся задачи:** клиент вычисляет следующий срок (4.3) и записывает новый `due`. Задача остаётся `active`.
- **«Завершить серию»** (только у повторяющейся): `status = done`, как у задачи без повтора.
- **Вернуть из выполненных:** `status = active`. Если срок уже прошёл, задача сразу просрочена, но без уведомления (4.4).
- **Удалить:** `status = deleted`, `deletedAt = serverTimestamp()`. **Восстановить:** `status = active`, `deletedAt = null`. **Удалить навсегда** из корзины: клиент удаляет документ.
- **Корзина:** раз в сутки сервер удаляет задачи с `status == deleted` и `deletedAt` старше 30 дней.
- **«Остановить пульсацию»:** `pulseMuted = true`. Сервер сбрасывает его в `false`, когда меняется `due`. Кнопка есть у любой активной задачи, которая сейчас мигает: наступило напоминание или прошёл срок.

### 4.2 Срок и часовой пояс

- `due.local` — время по часам без секунд и смещения; `due.tz` — зона IANA, в которой его нужно понимать. Момент срока — это `local`, интерпретированное в `tz`.
- Когда пользователь ставит или меняет срок, клиент записывает в `tz` текущую зону устройства. Другие правки задачи `due` не трогают.
- Когда пользователь ставит или меняет срок либо включает месячный повтор, клиент записывает в `repeat.monthDay` число месяца из `due.local`.
- Перенос срока повторяющейся задачи по «Готово» сохраняет её `tz` и `monthDay`.
- Клиенты показывают момент срока во времени текущей зоны устройства.
- Несуществующее местное время (весенний переход) сдвигается вперёд на длину перехода; неоднозначное (осенний переход) берётся с более ранним смещением — как `java.time.ZonedDateTime.of`. Веб обязан давать тот же результат; это проверяется общими примерами (раздел 11).

### 4.3 Следующий раз повторяющейся задачи

Вход: местное время срока L, зона Z, повтор `{ every: N, unit, weekdays: W }`, текущий момент `now`.

Один шаг из L в L′:
- `hours`: L′ = (момент L в зоне Z) + N часов реального времени, переведённое обратно в местное время Z;
- `days`: L′ = L + N дней; время суток сохраняется;
- `weeks` без `weekdays`: L′ = L + 7·N дней;
- `weeks` с непустым `weekdays` (ISO: 1 = пн … 7 = вс, неделя начинается с понедельника; пустой список равен отсутствию): если в неделе L есть день из W позже дня недели L — берётся ближайший такой день; иначе самый ранний день из W в неделе, отстоящей от недели L на N недель. Время суток сохраняется;
- `months`: месяц L′ = месяц L + N; число = `min(monthDay, последний день этого месяца)`; время суток сохраняется. Число всегда берётся от `monthDay`, а не от L, поэтому срок не «съезжает»: 31 января → 28 (29) февраля → 31 марта.

«Готово» повторяет шаг, начиная с L, пока момент L′ в зоне Z не станет позже `now`, и записывает первый такой L′. Пропущенные разы не накапливаются. Предохранитель — не больше 100 000 шагов.

Шаги `days`, `weeks` и `months` считаются по местному календарю, и результат записывается как есть, даже если это время попадает в переход на летнее время: момент определяется правилом 4.2 при чтении. Поэтому время суток не «съезжает» после перехода. Шаг `hours` идёт по реальному времени. Если полученный момент попадает во второй (повторный) час осеннего перехода, его местное время неоднозначно, поэтому такой шаг пропускается и берётся следующий.

### 4.4 Напоминания и просрочка (сервер)

- **События** активной задачи со сроком D: напоминание в момент D − m для каждого m из `reminders` и просрочка в момент D.
- **Уведомления отправляются только о событиях, наступивших после последнего изменения расписания задачи:** создания или смены `due`, `reminders`, `repeat`, `status`. При таком изменении `nextNotifyAt` = ближайшее событие строго позже текущего момента; события в прошлом не уведомляются. Если срок уже прошёл, сервер молча ставит `overdueAt` — задача видна как просроченная, но уведомление не отправляется. Это же защищает от повторной рассылки старых событий при переезде.
- **Проход планировщика:** для задачи с `nextNotifyAt <= now` обрабатываются только события с моментом в промежутке [`nextNotifyAt`, `now`]. После этого `nextNotifyAt` = ближайшее событие позже `now`; если событий нет, поле удаляется.
- **Напоминание:** из напоминаний в этом промежутке отправляется самое позднее — и только пока срок ещё не наступил: если момент D уже прошёл (планировщик опоздал), устаревшее напоминание не отправляется, приходит только «просрочено». Одно и то же (задача, срок, m) отправляется не больше одного раза (ключи в `notification-sent`); исключение — сбой прохода посреди отправки (см. «Недоставленное уведомление»). В тексте время до срока — в самых крупных целых единицах: часах, днях или неделях («За 1 годину до строку», «2 days before»).
- **Просрочка:** если момент D попал в промежуток и `overdueAt == null`, отправляется уведомление «просрочено» и ставится `overdueAt`.
- **Повторяющиеся задачи** ведут себя так же: сервер их срок не переносит.
- **Получатели:** устройства пользователя с `notificationsEnabled == true` и `fcmToken != null`. Язык текста — `settings.language`, при любом другом значении — `en`.
- **Сообщение:**
  - `data`: `type` (`reminder` или `overdue`), `taskId`, `title`, `body`, `minutesBefore` (только у напоминаний), `url` = `https://pmobile78.github.io/to-round-react/?taskId=<id>`;
  - `android`: `priority: high`, TTL — сутки;
  - `webpush`: TTL — сутки, `Urgency: high`, `fcmOptions.link = url`.
  
  Веб открывает задачу и по `?taskId=`, и по старому `?bubbleId=`.
- **Недоставленное уведомление** ([#93](https://github.com/PMobile78/to-round-react/issues/93)): ключ в `notification-sent` остаётся, только если уведомление получило хотя бы одно устройство. Нет получателей или все отправки не удались — `nextNotifyAt` не двигается, и следующие проходы повторяют попытку в течение 10 минут после момента события; потом событие отбрасывается (у просрочки `overdueAt` всё равно ставится). Если проход умер посреди отправки, его ключ остаётся незавершённым; через 2 минуты (проход живёт не дольше 60 секунд) следующий проход в пределах тех же 10 минут перехватывает ключ и отправляет снова — если умерший проход успел доставить уведомление, оно придёт дважды: дубль лучше пропуска.
- **Недействительный токен** (ошибки FCM `messaging/registration-token-not-registered` и `messaging/invalid-registration-token`): сервер ставит устройству `fcmToken = null`, если у устройства всё ещё этот токен. При других ошибках токен остаётся.

### 4.5 Категории

- **Создание:** `order` больше максимального, цвет — первый свободный в палитре.
- **Перестановка:** перенесённой категории записывается `order` между соседями (дробное число), остальные не меняются. Если соседние значения совпали, клиент одной пачкой перенумеровывает все категории.
- **Удаление:** клиент даёт 7 секунд на отмену, затем удаляет документ. Сервер убирает `categoryId` у задач этой категории.

## 5. Описания в Markdown

- Формат хранения — CommonMark плюс чек-листы (`- [ ]`, `- [x]`) и зачёркивание (`~~`) из GFM. Таблицы GFM не поддерживаются.
- Панели редакторов предлагают базовый набор: жирный, курсив, зачёркнутый, маркированный и нумерованный списки, чек-листы, ссылки. Остальной стандартный синтаксис — заголовки, цитаты, код, разделитель — клиенты показывают и сохраняют без потерь.
- Веб: визуальный редактор TipTap 3.x, StarterKit со стандартным синтаксисом, расширение чек-листов. Описание редактор читает расширением `@tiptap/markdown`, а сохраняет конвертером контракта `htmlToMarkdown` (`src/contract/markdown.js`): сериализатор `@tiptap/markdown` не экранирует начало строки, и текст «`\# текст`» при следующем открытии стал бы заголовком. Переключатель «простой / форматированный текст» удаляется. Расширения цвета, выделения маркером, подчёркивания, выравнивания, таблиц и картинок удаляются.
- Показ — документом схемы редактора: на экран попадает только то, что есть в схеме, сырой HTML разметкой не становится. Ссылки допускаются только со схемами `http`, `https` и `mailto`.
- Android — на этапе 2: просмотр с форматированием и правка текста Markdown. Удобное редактирование чек-листов отложено, до него Android не портит их синтаксис.

## 6. Сервер (Cloud Functions, регион europe-west1)

| Функция | Запуск | Что делает |
|---|---|---|
| `scheduleNotifications` | каждую минуту (`* * * * *`) | collectionGroup `tasks`, где `status == active` и `nextNotifyAt <= now`; обработка по 4.4 |
| `onTaskWritten` | запись `users/{uid}/tasks/{taskId}` | при создании и при смене `due`, `reminders`, `repeat` или `status` пересчитывает `nextNotifyAt`; если задача активна, срок уже прошёл и `overdueAt == null` — молча ставит `overdueAt`; при смене `due` ставит `pulseMuted = false`, а `overdueAt = null`, если новый срок в будущем или его нет; текущий момент — время записи, изменения считаются в транзакции от состояния до записи к текущему документу |
| `onCategoryDeleted` | удаление `users/{uid}/categories/{categoryId}` | ставит `categoryId = null` у задач этой категории, если категория с тем же id не создана снова |
| `purgeDeletedTasks` | раз в сутки (`0 3 * * *`, UTC) | удаляет задачи из корзины старше 30 дней |
| `cleanupNotificationSent` | каждый час | без изменений |

- `onTaskWritten` пишет только служебные поля (`nextNotifyAt`, `overdueAt`, `pulseMuted`) и не трогает `updatedAt`, поэтому не вызывает сам себя повторно.
- Планировщик и триггер записывают служебные поля в транзакции, заново прочитав задачу: если за время прохода пользователь изменил расписание, запись по устаревшим данным не делается.
- Ключи `notification-sent`: `reminder:{uid}:{taskId}:{m}:{due.local}@{due.tz}` и `overdue:{uid}:{taskId}:{due.local}@{due.tz}`. В id документа `/` из названия зоны записывается как `%2F`: Firestore не допускает `/` в id.
- Из collectionGroup `tasks` сервер берёт только документы `users/{uid}/tasks/{taskId}`: подколлекция с тем же именем в другом месте (например, внутри `user-mindmaps`, куда владелец пишет что угодно) не должна приводить к уведомлениям другому пользователю.
- Старые функции `scheduleDueDateNotifications` и `maintainNextNotifyAt` удаляются при переезде, вместе с ними — расчёт следующего повтора на сервере.
- Индексы для collectionGroup `tasks`: (`status`, `nextNotifyAt`) и (`status`, `deletedAt`).
- Тексты уведомлений — `functions/locales` (en, uk), как сейчас.

## 7. Правила Firestore

- Владелец (`request.auth.uid == uid`) читает и пишет `users/{uid}` и его подколлекции; остальным доступ закрыт.
- Для задач, категорий, устройств и документа пользователя проверяются:
  - набор полей: только допустимые, обязательные присутствуют;
  - типы, допустимые значения и ограничения из раздела 3;
  - `schemaVersion == 2`.
- Время создания и изменения:
  - при создании `createdAt` и `updatedAt` — не позже `request.time`, чтобы перенос и импорт сохраняли исходные даты;
  - при изменении `updatedAt == request.time`, а `createdAt` не меняется.
- `overdueAt` и `nextNotifyAt` клиент установить или изменить не может:
  - при создании `overdueAt == null`, а `nextNotifyAt` отсутствует;
  - при изменении оба поля равны прежним значениям.
- `deletedAt != null` тогда и только тогда, когда `status == "deleted"`.
- Списки проверяются по типу и размеру. `weekdays` дополнительно проверяется по допустимым значениям (`hasOnly([1..7])`). Значения `reminders` и `categoryIds` правилами поэлементно не проверить: это делают клиенты, а сервер пропускает некорректные напоминания.
- `user-mindmaps` — без изменений; `notification-sent` закрыта для клиентов.
- Старые коллекции `user-bubbles`, `user-tags`, `user-fcm-tokens` — только чтение для владельца.

## 8. Изменения в вебе

1. Новый слой данных для `users/{uid}/…`: преобразование «документ ↔ внутренняя модель» собрано в одном месте (`src/services/`). Внутренние имена в коде интерфейса (например, `tagId`) можно не переименовывать.
2. Удаляются копии задач и категорий в localStorage (`bubbles_{uid}`, `tags_{uid}`) и код, который с ними работает. Копия карт (`mindmaps_{uid}`) остаётся: код mindmap вне этапа.
3. Живая синхронизация холста ([#94](https://github.com/PMobile78/to-round-react/issues/94)): одна функция «документ → пузырь»; изменения обрабатываются по одному, без пересборки всего списка; добавление, изменение и удаление с другого устройства видны без перезагрузки и без дублей физических тел.
4. Категории — отдельные документы с `order`; перестановка записывает одну категорию.
5. Настройки — в `users/{uid}.settings`, запись по полям. При первом входе новой версии, если `settings` ещё нет, они заполняются из localStorage этого браузера (таблица 3.5), после чего эти ключи удаляются.
6. Срок хранится как `due {local, tz}` и показывается во времени устройства; пересчёт зон — через `Intl.DateTimeFormat`, без новых зависимостей. При выборе срока записывается зона устройства.
7. Повтор и напоминания без минут. У повторяющихся задач — «Готово» и «Завершить серию». Следующий раз считается по 4.3.
8. Описание — Markdown-редактор (раздел 5).
9. Устройства регистрируются по id установки Firebase. В настройках появляется переключатель «получать напоминания здесь». При выходе документ устройства удаляется.
10. Бэкап в формате v2 (раздел 10): импорт старого и нового форматов; без перезагрузки страницы ([#101](https://github.com/PMobile78/to-round-react/issues/101)); запись порциями не больше 450 операций, ошибки показываются пользователю ([#92](https://github.com/PMobile78/to-round-react/issues/92)).
11. Перенос данных при первом входе (раздел 9).

## 9. Перенос данных

### 9.1 Как работает

- Запускается, если у пользователя нет `users/{uid}.migration`, а в старых коллекциях есть данные.
- Сначала показывается окно предпросмотра, ничего не записывая:
  - число задач и категорий;
  - напоминания и повторы, округлённые до часа;
  - задачи, у которых теряется форматирование описания;
  - задачи, у которых теряется срок, напоминание или часть текста (нечитаемая дата, больше 10 напоминаний, слишком длинные название или описание);
  - категории, у которых меняется цвет;
  - некорректные записи, которые будут пропущены.
- Кнопки «Перенести» и «Отложить». «Отложить» выходит из аккаунта, окно появится при следующем входе.
- Запись идёт порциями не больше 450 операций и идемпотентна: повторный запуск пропускает задачи и категории, которые уже есть в `users/{uid}`, и дописывает остальные (перезаписать существующий документ правила не дают, раздел 7). В конце пишутся `settings` (если их ещё нет) и `users/{uid}.migration`.
- Старые коллекции не изменяются.
- Устройства не переносятся: каждое устройство заново регистрируется при входе.

### 9.2 Преобразование v1 → v2

Одно и то же преобразование используется и для переноса, и для импорта старых бэкапов.

**Задача:**

| v1 | v2 |
|---|---|
| `id` | id документа |
| `title` | `title` после обрезки пробелов; пустой → «Без назви» или «Untitled» по `settings.language` |
| `description` при `useRichText: true` | HTML → Markdown. Поддерживаемое форматирование сохраняется. Цвет, выделение маркером, подчёркивание, выравнивание и таблицы превращаются в обычный текст. Картинка → ссылка `[image](url)`; встроенная картинка (`data:`) отбрасывается |
| `description` при `useRichText: false` | текст с экранированием символов Markdown |
| `tagId` | `categoryId`; `null`, если такой категории нет |
| `status` | `active`, `done`, `deleted` как есть; `postpone` → `active` |
| `dueDate` и `tz` | `due = {local, tz}`. `local` — первые 16 символов строки (без секунд). Строка с `Z` или смещением переводится в местное время `tz`. Если `tz` нет — берётся зона браузера на момент переноса |
| `notifications[]` | `reminders`. `5m`, `10m`, `15m`, `1h` → 60; `1d` → 1440. `{type: "custom", value, unit}`, число и `{minutesBefore}` → минуты, округлённые вверх до целого часа, минимум 60. Без повторов, по возрастанию, не больше 10; без срока → `[]` |
| `recurrence` | `repeat`. `minutes` → `hours` с `every = ceil(every / 60)`. `weekDays` (0 = вс … 6 = сб) → `weekdays` ISO (0 → 7). Для `months` — `monthDay` = число месяца из срока. Без срока → `null` |
| `radius` | `radius`, приведённый к 30–80; если нет — 45 |
| `overduePulseSuppressed` | `pulseMuted` |
| `createdAt`, `updatedAt`, `deletedAt` | `Timestamp` из ISO-строки. Некорректное значение или время из будущего → время переноса. У неудалённой задачи `deletedAt` всегда `null` |
| `fillStyle`, `strokeStyle`, `useRichText`, `overdueSticky`, `overdueAt`, `nextNotifyAt` | не переносятся; задача создаётся с `overdueAt: null` и без `nextNotifyAt`, служебные поля сервер выставит заново (4.4) |

**Категория:** `{id, name, color}` → документ с тем же id. `name` обрезается по пробелам; пустое имя → «Category». `order` — порядок как в старом массиве, номера 1, 2, 3… без пропусков (пропущенные записи не занимают номер). Если `color` не из палитры или повторяется, выбирается первый свободный цвет палитры, и категория попадает в предпросмотр. Если свободных цветов нет, категория не переносится, а её задачи остаются без категории.

**Настройки:** из localStorage браузера, где идёт перенос (таблица 3.5); отсутствующие ключи получают значения по умолчанию.

### 9.3 Бэкап, репетиция, переезд, проверка, откат

1. **Бэкап.** Владелец делает экспорт в текущей версии веба и сохраняет файл в `/media/big_disk/Backup/to-round/` (вне git). Старые коллекции не изменяются и служат второй копией.
2. **Репетиция.** Экспорт загружается в эмулятор Firebase, в старые коллекции. Новая версия веба запускается против эмулятора и выполняет перенос целиком. Результат сравнивается с исходными данными: числа, выборочные задачи, расписание напоминаний. Повторяется, пока всё не совпадёт.
3. **Переезд.** Индексы выкатываются заранее, и окно начинается, когда они готовы: веб v1 они не мешают. Окно 15–30 минут: задачи не править, напоминания могут не прийти.
   1. Выкатить правила: новые пути, старые коллекции — только чтение.
   2. Выкатить функции v2; старые функции удаляются.
   3. Выкатить веб v2 через `deploy-prod.yml`.
   4. Владелец входит, смотрит предпросмотр и нажимает «Перенести».
4. **Проверка.**
   - Число задач и категорий совпадает с бэкапом.
   - 3–5 задач сверяются вручную.
   - Тестовая задача со сроком через 61 минуту и напоминанием «за 1 час» даёт уведомление через минуту.
   - Задача, созданная во второй вкладке или на телефоне, появляется без перезагрузки.
5. **Откат.** Вернуть прежние версии правил, функций и веба; индексы остаются — в их файле есть и индекс v1. Старые данные целы. Изменения, сделанные после переезда, теряются — поэтому окно короткое. В браузерах, где открывался v2, старых ключей настроек уже нет (раздел 8, п. 5): v1 покажет там настройки вида по умолчанию.
6. **Удаление старых коллекций** — вручную владельцем, когда Android-приложение уже в работе. Инструкция — [docs/migration.md](../../migration.md#старые-коллекции).

## 10. Формат бэкапа v2

```json
{
  "format": "to-round-backup",
  "version": 2,
  "exportedAt": "2026-10-14T12:00:00.000Z",
  "settings": { "themeMode": "system", "design": "classic", "language": "uk" },
  "categories": [
    { "id": "k3j9x0abc", "name": "Дом", "color": "#E57373", "order": 1 }
  ],
  "tasks": [
    {
      "id": "p0q8r7stu",
      "title": "Оплатить счета",
      "description": "- [ ] свет\n- [ ] вода",
      "categoryId": "k3j9x0abc",
      "status": "active",
      "due": { "local": "2026-10-15T09:00", "tz": "Europe/Kyiv" },
      "reminders": [60],
      "repeat": { "every": 1, "unit": "months", "monthDay": 15 },
      "radius": 45,
      "pulseMuted": false,
      "createdAt": "2026-10-01T08:00:00.000Z",
      "updatedAt": "2026-10-10T19:30:00.000Z",
      "deletedAt": null
    }
  ]
}
```

- В примере `settings` сокращён: в файле он содержит все поля из 3.5.
- Служебные поля (`schemaVersion`, `overdueAt`, `nextNotifyAt`) в бэкап не пишутся. Время — в ISO-строках.
- Импорт принимает v2 и v1 (через 9.2).
- Весь файл проверяется до любых записей, как сейчас ([#91](https://github.com/PMobile78/to-round-react/issues/91)). Запись, которую нельзя прочитать (в том числе запись файла v1 без id или с повтором id), отклоняет весь файл. Время из будущего заменяется временем чтения файла, как в 9.2; зону срока, которую браузер не знает, импорт принимает, как и правила (раздел 7).
- Перед записью — подтверждение с числами.
- Импорт заменяет все задачи и категории, а если в файле есть `settings` — и настройки. Замена: записи, которых нет в файле, удаляются (`deleteDoc`); существующие с тем же id обновляются `updateDoc` (без `createdAt` и служебных полей сервера, `updatedAt` — время сервера); новые создаются с исходными `createdAt` и `updatedAt`. Удалять и создавать заново существующие записи нельзя: `onCategoryDeleted` после удаления категории может обнулить `categoryId` у уже восстановленных задач.
- Запись идёт порциями не больше 450 операций, ошибки показываются, страница не перезагружается.

## 11. Проверка

- Папка `contract/` в корне репозитория. Её читают тесты веба (vitest), функций и позже Android (JUnit):
  - `palette.json` — 20 цветов категорий;
  - `fixtures/` — правильные и неправильные документы задач, категорий, устройств и настроек;
  - `fixtures/migration-v1.json` — пары «v1 → ожидаемый v2», включая округление минут, HTML → Markdown и дни недели;
  - `fixtures/recurrence.json` — «срок, повтор, now → следующий срок», включая переходы на летнее время и месячный повтор с `monthDay` 29–31 через короткие месяцы. Для переходов берутся зоны со стабильными правилами (`America/New_York`, `Europe/Berlin`): алгоритм от зоны не зависит, а правила `Europe/Kyiv` могут измениться в tzdata;
  - `fixtures/time.json` — «local + tz → момент» для несуществующего и неоднозначного времени.
- **Правила:** `@firebase/rules-unit-testing` на эмуляторе — разрешённые и запрещённые записи для каждого типа документа ([#99](https://github.com/PMobile78/to-round-react/issues/99), часть про правила).
- **Функции:** расписание событий, молчаливая просрочка, выбор получателей, содержимое сообщений, каскад при удалении категории, очистка корзины.
- **Веб:** слой данных, настройки, перенос (предпросмотр и результат), импорт и экспорт, синхронизация холста.
- **Общая проверка** — `npm run verify`; тесты правил на эмуляторе входят в неё.
