# Этап 1: основа Android-приложения — спецификация

Дата: 2026-10-22. Статус: на согласовании.
Связано: [дорожная карта](2026-10-14-android-roadmap.md), [контракт данных v2](2026-10-14-stage-0-data-contract-v2-design.md), [обзор подпланов](../plans/2026-10-22-stage-1-overview.md).

## 1. Цель

Заложить основу нативного Android-приложения и доказать, что оно совместимо с вебом на тех же данных:

- проект `android/`, который собирается и ставится на телефон;
- вход, регистрация, сброс пароля и выход через Firebase Auth;
- слой данных по контракту v2, проверенный на общих примерах из `contract/`;
- один экран — список активных задач, только для просмотра.

Этап готов, когда:

- владелец входит на Redmi 9 в свой аккаунт и видит те же задачи, что во вкладке «Активные» веба: столько же задач, в том же порядке, с теми же категориями и сроками;
- тесты Android (`android/gradlew -p android check`) проходят.

## 2. Решения

### 2.1 Принятые раньше

Из [дорожной карты](2026-10-14-android-roadmap.md):

- Kotlin и Jetpack Compose, Firebase Android SDK.
- Тот же проект Firebase `todo-flutter-fb8bf` и тот же формат данных v2, что у веба. Веб продолжает работать.
- Монорепо: код в `android/` этого репозитория, общий контракт — в `contract/`.
- `applicationId` — `com.pmobile78.toround`, название — «ToDo-Round».
- `minSdk` 26 (Android 8.0); `compileSdk` и `targetSdk` — актуальный API.
- Material 3 в цветах To-Round.
- Вход по email и паролю; вход через Google — возможно, на этапе 6.
- Проверка — на телефоне Redmi 9 (Android 12) и эмуляторе `ToRound_API37`.

### 2.2 Умолчания этапа 1

Владелец пропустил вопросы (2026-10-22), поэтому решения ниже принял исполнитель. Любое из них можно поменять до исполнения подплана, к которому оно относится.

| № | Тема | Решение | Почему |
|---|---|---|---|
| 1 | Модули | `core` — чистый Kotlin без Android и Firebase: модели и правила контракта. `app` — Android-приложение | Правила контракта проверяются за секунды без телефона и не могут случайно зависеть от Android |
| 2 | Сборки | Один `applicationId` у отладочной и релизной сборки | Одна регистрация в Firebase, одно приложение на телефоне |
| 3 | Название | Gradle при сборке берёт его из `src/appName.js` | Правило проекта: название задаётся в одном месте |
| 4 | Цвета и иконка | Цвета дизайна «classic» веба: основной `#3B7DED`, акцент `#FF6B6B`, фон `#f5f5f5` / `#121212`, панели `#ffffff` / `#1e1e1e`. Цвета обоев Android (Material You) не используются. Иконка — три пузыря веб-иконки, нарисованные вектором | Приложение выглядит как To-Round, а не как обои телефона; вектор чёткий на любом экране |
| 5 | Язык и тема | До входа — язык, выбранный на экране входа (переключатель EN/UK, как в вебе; сначала — язык телефона), и системная тема. После входа — `settings.language` и `settings.themeMode` аккаунта | Так работает веб (контракт, раздел 3.5) |
| 6 | Состав списка | Как вкладка «Активные» веба: все задачи `active` с сохранёнными в вебе фильтром `listFilter` и сортировкой `listSort`. Описание задачи не показывается | Тот же набор и порядок — прямое сравнение с вебом; Markdown появится на этапе 2 |
| 7 | Записи в Firestore | Единственная запись этапа — документ `users/{uid}` для аккаунта, у которого его ещё нет (контракт, раздел 3.4) | У аккаунта владельца документ уже есть, поэтому приложение в прод не пишет |
| 8 | Перенос из v1 | Приложение данные v1 не переносит | Перенос делает веб; аккаунт без переноса увидит пустой список |
| 9 | `google-services.json` | Хранится вне git, как `.env` веба; скачивается командой Firebase CLI | Правило проекта: настройки Firebase не коммитятся |
| 10 | Регистрация в Firebase | Исполнитель регистрирует `com.pmobile78.toround` командами Firebase CLI — только после «да» владельца в начале подплана 1.2. Владелец может сделать это и сам в консоли. Старая регистрация `com.hb.todoflutter` (от прежнего Flutter-проекта) остаётся как есть | Изменение проекта Firebase — решение владельца |
| 11 | Релизный ключ | Владелец создаёт его одной командой из инструкции; пароль знает только он; файл ключа лежит вне репозитория и в бэкапе. Пока ключа нет, на телефон ставится отладочная сборка | Пароль от ключа — секрет владельца |
| 12 | Тесты в общей проверке | Тесты Android не входят в `npm run verify` и CI: им нужен Android SDK. У Android своя команда | Веб и его CI не меняются |
| 13 | Аналитика | Без Firebase Analytics и Crashlytics | В этапе 1 не нужны; при публикации в Play меньше данных для раздела «Безопасность данных» |

## 3. Проект `android/`

```
android/
  settings.gradle.kts, build.gradle.kts, gradle.properties
  gradle/libs.versions.toml      версии библиотек и плагинов
  gradle/wrapper/…, gradlew      Gradle Wrapper
  core/                          чистый Kotlin (JVM): модели и правила контракта v2
  app/                           приложение: Compose, Material 3, Firebase
```

- **Версии** — последние стабильные на момент подплана. Android Gradle Plugin — не новее того, что поддерживает установленная Android Studio: Rabbit 1 (2026.2.1) понимает AGP до 9.4.
- **JDK** — JBR из Android Studio (`/media/big_disk/android/android-studio/jbr`). Байт-код — Java 17.
- **SDK:** `minSdk` 26; `compileSdk` и `targetSdk` — 37, платформа уже установлена.
- **Пакеты:** `com.pmobile78.toround` (app) и `com.pmobile78.toround.core` (core).
- **Строки** — `values/` (английский, по умолчанию) и `values-uk/`. Тексты по возможности совпадают с `src/locales` веба.
- **Подпись.** Debug — стандартный ключ Android (`~/.android/debug.keystore`; `~/.android` уже ссылается на big_disk). Release — сжатие R8 и ключ, путь и пароли которого Gradle читает из `~/.gradle/gradle.properties`, то есть вне репозитория. Без этих настроек релизная сборка собирается неподписанной.
- **Команды** — из корня репозитория:
  - `android/gradlew -p android check` — все тесты JVM и Android Lint;
  - `android/gradlew -p android :app:installDebug` — поставить отладочную сборку на подключённое устройство.
- **`.gitignore`** в `android/`: результаты сборки, `.gradle/`, `local.properties`, `google-services.json`, файлы ключей.
- **Документация.** Новый `docs/android.md`: сборка, установка на телефон, режим разработчика в MIUI, релизный ключ, эмуляторы Firebase. Ссылки на него — в `docs/README.md` и `CLAUDE.md`. В `contract/README.md` Android появляется среди читателей примеров, а в правило «изменили пример — прогоните тесты всех клиентов, которые его читают» добавляется команда Android.

## 4. Ядро контракта (`core`)

Чистые функции и модели без Android и Firebase. Они повторяют `src/contract/*` веба и проверяются на тех же примерах.

- **Схема:**
  - константы и ограничения из раздела 3 контракта: статусы, единицы повтора, темы, дизайны, языки, главный вид, поля сортировки, лимиты, радиус по умолчанию;
  - палитра — тест сверяет её с `contract/palette.json`;
  - `normalizeLanguage`: `uk*` → `uk`, иначе `en`;
  - настройки по умолчанию — тест сверяет их с примером `defaults` из `contract/fixtures/settings.json`.
- **Время:** разбор и запись `YYYY-MM-DDTHH:mm`, проверка зоны, «местное время + зона → момент» и обратно. Работает на `java.time` — это эталон контракта. Примеры — `contract/fixtures/time.json`.
- **Проверка записей.** Задача, категория и настройки проверяются в форме бэкапа (раздел 10 контракта) по тем же правилам и с теми же текстами ошибок, что `src/contract/validate.js`:
  - правильные примеры из `tasks.json`, `categories.json`, `settings.json` принимаются, неправильные — отклоняются;
  - «поля нет» и «поле равно `null`» — разные случаи, как в JavaScript;
  - целое число — как в JavaScript: число без дробной части;
  - проверка зоны срока — параметр. Тесты на примерах используют строгую проверку, как веб. Чтение из Firestore допускает зону, которой нет в базе часовых поясов телефона: правила Firestore её принимают, и задача не должна пропасть из списка.
- **Модели** — задача (со сроком и повтором), категория, настройки (с фильтрами и сортировкой). Строятся только из проверенной записи.
- **Правила списка** (подплан 1.3): фильтр и сортировка вкладки «Активные» веба (раздел 7).
- **Не входят в этап:**
  - следующий повтор (`recurrence.json`) — этап 2;
  - устройства (`devices.json`) — этап 3;
  - Markdown и перевод v1 (`markdown-v1.json`, `migration-v1.json`) Android не нужны: перенос делает веб.

## 5. Firebase

- **Регистрация** (решение 10). Android-приложение `com.pmobile78.toround` в проекте `todo-flutter-fb8bf` и SHA-1 отладочного ключа. Для входа по email и паролю SHA-1 не обязателен, но понадобится для входа через Google — добавляем сразу. SHA-1 релизного ключа — когда ключ появится.
- **`google-services.json`** лежит в `android/app/` вне git. Скачивается командой `firebase apps:sdkconfig ANDROID <appId>`. Без файла `app` не собирается — `docs/android.md` объясняет, где его взять.
- **Вход и выход** — как в вебе:
  - вход: email и пароль;
  - регистрация: имя, email, пароль и повтор пароля; пароль — не короче 6 символов; имя записывается в профиль Firebase Auth;
  - «Забыли пароль?» отправляет письмо на языке приложения (`setLanguageCode`), без ссылки «Продолжить»: вернуться по ней в приложение нельзя;
  - выход — пункт меню с подтверждением;
  - ошибки Firebase показываются понятными текстами на языке приложения (те же случаи, что в `authService.js`).
- **Firestore:** офлайн-кэш (по умолчанию в SDK) и живые подписки.
- **Эмуляторы Firebase.** Отладочная сборка с ключом Gradle `-Ptoround.emulators=true` ходит в Auth- и Firestore-эмуляторы на компьютере: с эмулятора Android — по адресу `10.0.2.2`, с телефона — через `adb reverse`. Тесты на эмуляторах используют отдельный проект `demo-to-round` и в прод не ходят.

## 6. Слой данных (`app`)

- **Что читается:** только `users/{uid}`, `users/{uid}/tasks` и `users/{uid}/categories`.
- **Преобразование документа:**
  - `Timestamp` → ISO-время, как `taskFromDoc` веба;
  - числа Firestore (целые приходят как `Long`, дробные — как `Double`) → числа записи бэкапа;
  - затем проверка ядром → модель;
  - время сервера, которое ещё не подтверждено, читается оценкой (как `serverTimestamps: 'estimate'` веба).
- **Документ, который не проходит проверку,** в список не попадает. Экран показывает, сколько таких документов: в этапе проверки совместимости расхождения должны быть видны.
- **Репозитории:**
  - задачи — живой список всех задач пользователя;
  - категории — живой список;
  - настройки — из документа пользователя; поле без значения получает значение по умолчанию, как `settingsFromUserDoc` веба.
- **Документ пользователя.** Если документа нет и это подтвердил сервер (не только кэш), приложение создаёт его, как веб (контракт, раздел 3.4):
  - `schemaVersion: 2`;
  - все поля `settings` по умолчанию, язык — текущий язык экрана;
  - `createdAt` и `updatedAt` — время сервера.

  Существующий документ не перезаписывается; правила Firestore и так отклоняют такую запись.
- **Проверка записи** — на эмуляторе Firestore с настоящими `firestore.rules` из репозитория.

## 7. Экран списка

- **Верхняя панель:** название приложения и меню с пунктом «Выйти».
- **Набор задач** — как во вкладке «Активные» веба:
  - задачи со `status == "active"`, в том числе запланированные (со сроком в будущем);
  - фильтр `settings.listFilter`: `categoryIds: null` — все категории; задача со ссылкой на несуществующую категорию считается «без категории».
- **Порядок** — `settings.listSort` по тем же правилам, что `TaskList.jsx`:
  - название и имя категории сравниваются без учёта регистра;
  - `updatedAt` без значения заменяется на `createdAt`;
  - время сравнивается с точностью до миллисекунды, как `Date` в JavaScript;
  - при равенстве задачи идут в порядке id документов — в том же порядке веб получает их при загрузке.
- **Строка задачи:**
  - название;
  - срок: дата и время во времени телефона; если момент срока прошёл — красным, с отметкой «Просрочено»;
  - категория: цвет и имя.
- **Над списком** — число задач. Если фильтр из веба скрывает часть задач, — «Показано N из M».
- **Состояния:**
  - загрузка;
  - пустой список: «Нет активных задач»;
  - данные только из кэша, без связи с сервером — заметка об этом;
  - документы, которые не прошли проверку, — заметка с их числом.
- **Обновление.** Список обновляется сам, когда задачи меняются на других устройствах.
- **Нажатие на задачу** в этапе 1 ничего не делает.
- **Зона, которой нет в базе телефона.** Срок показывается так, как записан (`due.local`), без пересчёта и без отметки просрочки.

## 8. Язык и тема

- **До входа:**
  - язык — выбранный переключателем на экране входа; сначала — язык телефона (`uk*` → украинский, иначе английский);
  - тема — системная.
- **Новый аккаунт** получает язык экрана входа (контракт, раздел 3.5).
- **После входа:**
  - применяются `settings.language` и `settings.themeMode` аккаунта;
  - изменения, сделанные в вебе, применяются сразу.
- **Механизм** — языки приложения AppCompat (`setApplicationLocales`). Он работает на Android 12 телефона и новее.

## 9. Проверка

- **`core`** — JUnit на примерах `contract/`: `time.json`, `tasks.json`, `categories.json`, `settings.json`, `palette.json`; плюс правила списка (фильтр и сортировка).
- **`app`** — JUnit:
  - преобразование документов Firestore: целые, дробные, `Timestamp`, отсутствующие поля и поля со значением `null`;
  - применение настроек.
- **На эмуляторах Firebase** — тесты на Android-устройстве (`connectedDebugAndroidTest`):
  - чтение документов в той форме, в какой их пишет веб;
  - создание документа пользователя под настоящими правилами;
  - отказ правил при перезаписи существующего документа.

  Тесты запускаются на эмуляторе `ToRound_API37` или на телефоне.
- **Android Lint** — без ошибок.
- **Проверка вживую:**
  - подплан 1.1 — приложение открывается на эмуляторе, а если телефон подключён, то и на телефоне;
  - подплан 1.2 — вход, регистрация, сброс пароля и выход на эмуляторах Firebase;
  - подплан 1.3 — владелец на Redmi 9 со своим аккаунтом сравнивает список с вебом: число задач, порядок, 3–5 задач по названию, категории и сроку.

## 10. Шаги владельца

1. **Подплан 1.1, по желанию.** Включить на Redmi 9 режим разработчика и отладку по USB. В MIUI нужны ещё «Установка через USB» и «Отладка по USB (настройки безопасности)». Затем подключить телефон к компьютеру. Инструкция — в `docs/android.md`.
2. **Подплан 1.2.** Сказать «да» на регистрацию приложения в Firebase командами CLI — или зарегистрировать его самому в консоли.
3. **Когда удобно.** Создать релизный ключ одной командой из инструкции. Пароль и файл ключа сохранить в надёжном месте.
4. **Подплан 1.3.** Войти на телефоне в свой аккаунт и сравнить список с вебом.

## 12. Вне этапа

- Правка задач, категорий и настроек; вкладки, поиск, описания в Markdown — этап 2.
- Устройства, FCM и уведомления — этап 3.
- Экран пузырей и пять дизайнов — этап 4.
- Экспорт и импорт бэкапа, смена пароля, «О приложении» — этап 5.

## 13. Риски

| Риск | Что делаем |
|---|---|
| MIUI не ставит приложения по USB без «Установка через USB», а этот пункт требует входа в Mi-аккаунт | Инструкция в `docs/android.md`; запасной путь — скопировать APK на телефон и поставить его вручную |
| 14 ГБ памяти не хватает на эмулятор Android вместе с Android Studio | Эмулятор запускается без окна и без Android Studio и закрывается после проверки; у Gradle ограничена память |
| Новый AGP не откроется в установленной Android Studio | AGP не новее того, что она поддерживает (сейчас 9.4) |
| Числа Firestore приходят как `Long` и `Double`, а не как числа JavaScript | Преобразование покрыто тестами (раздел 9) |
| База часовых поясов телефона старее, чем у браузера | Зона без пересчёта (раздел 7), чтение не отклоняет задачу |
| Без `google-services.json` свежий клон не собирает `app` | Инструкция в `docs/android.md` и понятная ошибка сборки |
